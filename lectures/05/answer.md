## 演習

- 回答モデル（実行時の`[model]`）：gemini-3.5-flash-lite
- 比較した質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」（期待する根拠：第2回 PDF p.52）
- 対象資料（全文投入と他の方式で範囲が違う点も記録）：全文投入は全9資料・438ページ（入力227,971文字）。ベクトル検索・Tree・Graphは第1〜3回の本講義・214ページ。範囲がそろっていないため、厳密な方式比較ではない。ベクトル検索は `RAG_TOP_K = 5`（初期値）で実行。

| 方式 | 回答の要点・正しさ | 引用ページと根拠 | 時間（秒） | 入力／出力トークン数 | モデル応答回数 | 生成API推定費用（USD） |

- 検索だけを実行して見つかったページと、その本文で確認できたこと：`uv run python -m app.retrieval "LoRA QLoRA 違い"` で上位5件は p.52（LoRAとQLoRA）、p.51（PEFT）、p.60（第2回演習の概要）、p.47（知識の追加はRAGが効きやすい）、p.61（演習の進め方）。p.52の本文に「元の重みは固定し、小さな差分だけを学習（LoRA）」「さらに元の重みを4bitに圧縮（QLoRA）」とあり、答えの根拠は1位で取れていた。p.51も補強になるが、p.60・p.47・p.61は話題が近いだけで答えには不要。
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  - ベクトル検索：`search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` を1回
  - Tree：`browse_tree` を4回。講義一覧 → `lec02-main`（基盤モデルの仕組み）→ `lec02-main-s045`（選んだモデルを、いつ・どう直すか）→ `lec02-main-p052` で本文717文字を取得
  - Graph：`search_graph({'query': 'LoRA QLoRA 固定 学習'})` を1回（seeds と expanded をまとめて取得）
  - 全文投入：ツール呼び出しなし（モデル応答1回）
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：全文投入では根拠を含む資料をすべて入力できていた（上限エラーなし）のに、回答が「資料のp.52を確認してください」という案内にとどまり、本文の内容を直接使って答えきれなかった。入力が約11.7万トークンと大きく、必要な情報が埋もれた可能性がある。ベクトル検索の結果にも、p.60・p.47・p.61 など回答に使われないページが含まれていた。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：単一ページで答えられる質問ならベクトル検索を採用したい。正答で、入力トークン・費用が最も小さく（全文投入の約1/39のトークン）、時間も短い。Graphも同程度の負担で p.51 まで拾えたので、複数ページにまたがる質問向けの候補にしたい。Treeは正答だが、応答5回で時間・費用が増える。限界：質問は1問のみ、各方式1回ずつの実行で、全文投入だけ対象資料の範囲が広い。
- 気づき・疑問：全文を渡せば正しく答えられるわけではなく、「入ること」と「使われること」は別だと確認できた。Treeは目次の見出しだけで正しいページにたどり着けたが、章をまたぐ質問でも同じようにたどれるのかが疑問。

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K` を 5 → 10 に変更し、同じ質問を `--trace` 付きで実行して変更前後を比較した。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」
  - モデル：gemini-3.5-flash-lite（変更前後で同じ）
  - 対象資料：第1〜3回の本講義資料（`search_materials` による通常のベクトル検索）
  - 変えたのは `RAG_TOP_K` のみ
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

| 項目 | 変更前（K=5） | 変更後（K=10） |
|---|---|---|
| ツール呼び出し | `search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` 1回 | 同じ（1回・同じquery） |
| 引用ページ | 第2回 p.52 | 第2回 p.52, p.51 |
| 回答の要点 | LoRA＝元の重みを固定し小さな行列A・Bのみ学習／QLoRA＝元の重みを4bitに圧縮 | 同じ内容＋「メモリ削減でGPU 1台（Colab等）でも大きなモデルを調整できる」という補足 |

| 入力／出力トークン | 3,028 / 154 | 5,189 / 234 |
| モデル応答回数 | 2 回 | 2 回 |
| 生成API推定費用 | $0.001293 | $0.001594 |

- 改善した例と、残る失敗・制約：
  - 改善：K=10 で p.51 も取得され、QLoRA の目的（メモリ削減・GPU 1台での調整）まで根拠付きで説明できるようになった。
  - 制約：質問の核心（固定するもの・学習するもの・QLoRAで加えるもの）は K=5 の p.52 だけで答えられており、増えた検索結果の多くは回答に使われていない。それでも入力トークンは約1.7倍（+2,161）、推定費用は約1.2倍に増えた。
  - 制約：変更前後とも1回ずつの実行なので、時間の差（3.68→3.30秒）はAPI応答のばらつきの範囲と考えられる。
- 気づき・疑問：
  - `RAG_TOP_K` を変えてもツールの呼ばれ方（回数・query）は変わらず、変わるのは1回の検索で返る件数だけだった。
  - K を増やすと補足情報は拾えるが、不要なページも入力に入るのでコストが増える。単一ページで答えられる質問では K=5 で十分だった。
  - 疑問：章をまたぐ質問など、根拠が複数ページに散らばる質問では、K を増やす効果がもっと大きいのか。質問の種類に応じて K を変える仕組みは作れるか。
