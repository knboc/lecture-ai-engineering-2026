## 演習

### やったこと
- 評価セット（data/eval/lec04_cases.jsonl、10件）に、自分で4つの基準（根拠・範囲・ヒント・分かりやすさ）と「回の表示」のラベルを付けた（labels.jsonl）
- `uv run python -m app.judge` で LLM（gemini-3.5-flash-lite）に採点させ、自分のラベルとの一致率を見た
- rubric.md は直していない（直す代わりに、宿題でモデルを変えて比べた）

### 結果（元の設定：gemini-3.5-flash-lite）
- 基準別の一致率：根拠 8/9（要確認 1）、範囲 10/10、ヒント 10/10、分かりやすさ 9/9（要確認 1）、回の表示（コード）10/10
- 総合の一致率 9/9、coverage 90%（自動判定できた 9/10 件）
- 要確認 2件（どちらも #08：根拠、分かりやすさ）
- 不一致 1件（#06 根拠、過検出：LLM=不合格、自分=合格）

### 気づき
- 「回の表示」はコード判定で、自分のラベルと全件一致した。末尾に「第N回」があるかは、文字列で決まるため
- LLM は、宿題の答えのコードを出した回答（#06）を、「ヒント」だけでなく「根拠」の失敗にも数えた
- 指示を無視した回答（#08）は、基準だけでは決めにくく、LLM が unsure にした

## 宿題

### レベル
基礎

### やったこと
- 採点のモデル（AIE_MODEL）を既定の gemini-3.5-flash-lite から gemini-3.5-flash に変えて、app.judge を再実行した（rubric.md、judge.py、labels.jsonl は変更なし）
- 自分で付けたラベル（labels.jsonl、10件）に対する、基準別の一致率と要確認の件数を比べた

### 結果
| 項目 | 変更前（gemini-3.5-flash-lite） | 変更後（gemini-3.5-flash） |
|---|---|---|
| 根拠 | 8/9（要確認 1） | 8/9（要確認 1） |
| 範囲 | 10/10 | 10/10 |
| ヒント | 10/10 | 10/10 |
| 分かりやすさ | 9/9（要確認 1） | 10/10 |
| 回の表示（コード） | 10/10 | 10/10 |
| 総合・coverage | 9/9、90% | 9/9、90% |
| 要確認の件数 | 2件（#08 根拠、#08 分かりやすさ） | 1件（#05 根拠） |
| 不一致 | 1件（#06 根拠、過検出） | 1件（#08 根拠、過検出） |

### 気づき・疑問
- 要確認は2件から1件に減り、「分かりやすさ」の要確認がなくなった。一方、総合の一致率と coverage は変わらなかった（10件・1回ずつなので、モデルの優劣は言えない）
- 要確認の項目が #08 から #05 に変わった。#05 は rubric.md の「まだ決めていないこと」に当たる件で、flash はその規則どおりに unsure にした。lite は #08（指示違反の回答）の方を unsure にした
- 不一致はどちらも「根拠」の過検出で、見逃しは0件だった。LLM は甘いのではなく、厳しめに判定した
- どちらのモデルも、指示違反や宿題の答えを出した回答（#06、#08）を、「範囲」「ヒント」だけでなく「根拠」の失敗にも数えた。観点が混ざっている。rubric.md の「根拠」に「指示違反は範囲で見る」と書き足すと減るかもしれない（試していない）
- 疑問：一致率が同じでも、不合格を見抜けているとは限らない。不合格の再現率を、件数を増やして見る必要がある
